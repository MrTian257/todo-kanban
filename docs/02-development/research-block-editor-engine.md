## 0 证据纪律与体积数字的测量方法（怎么复查）

- **只认主源**：官方文档站（prosemirror.net / tiptap.dev / lexical.dev / blocknotejs.org / docs.slatejs.org）、GitHub 或自托管 forge 的源码与 issue/PR、npm registry 元数据（`registry.npmjs.org/<包>`：版本、发布日期、`license`、`dependencies`、`peerDependencies` 的权威来源）、以及本仓库源码。未采用任何二手博客或 AI 摘要。凡主源查不到的，一律写「未证实」并注明查过哪里。
- **未跑本仓库构建**：按用户约定，本次没有执行 `npm install` / `npm run build` / `npm test` / `cargo`，没有启动 dev server，没有改任何产品代码。因此 §5 的 Markdown 往返结论全部是「官方声明 + issue 证据 + 依赖清单推断」，逐条实跑列为需实测项。
- **gzip 数字怎么来的**（可复现）：从 npm registry 下载各候选**最新稳定版**发布物 → 在**仓库外的临时目录**（本机 `%LOCALAPPDATA%\Temp\blk-res\node_modules`，保留未删，可直接复查）拼 `node_modules` → 用本仓库已装的 **esbuild 0.28.2** 对「只 import 该候选公开入口」的最小入口做 `{bundle, minify, format:esm, target:es2020, define:process.env.NODE_ENV=production}` → 产物**逐候选单次 gzip** 计数。口径注意：① 这是**首次引入**的 JS 增量，`react`/`react-dom` 设 external（已在主包内）；② CSS 与字体不计入 JS 数字、表内单列；③ 用了 `import * as X` 的候选（BlockNote、`@lexical/mdast`）是**上界**，按需引入会更小；④ 与真实 `npm run build` 产物预计有 ±10% 出入。
- **现状基线（本仓库实测，非官方口径）**：`import Vditor from "vditor"` + `import "vditor/dist/index.css"` 打进包内为 **min 294.7 KB / gzip 73.2 KB**；运行期再从 `public/vendor/vditor` 按需拉 `dist/js/lute/lute.min.js` **587.6 KB gzip**、`dist/js/highlight.js/highlight.min.js` **295.9 KB gzip**、`dist/js/icons/ant.js` **11.8 KB gzip**、`dist/js/i18n/zh_CN.js` **1.2 KB gzip**（逐文件 gzip，取自本地已装的 `node_modules/vditor@4.0.0` 发布物）。vendored 目录整体 **19.62 MB / 356 文件**（由 [scripts/sync-vditor-assets.mjs](../../scripts/sync-vditor-assets.mjs) 只复制 `js/css/images` 三目录并排除 `.map` 与字体）。主包现状 **约 1.5 MB / gzip 484 KB**，构建已有 1500 KB 警告（票正文给的数）。

## 1 结论先行

六个候选没有一个「开箱即满足」ADR-0001 的全部口径，但**违反的层次完全不同**：BlockNote 官方直接把 Markdown 导入导出定性为 *lossy*、非 lossy 路径就是 `JSON.stringify(editor.document)`（[export 文档](https://www.blocknotejs.org/docs/features/export/markdown)／[import 文档](https://www.blocknotejs.org/docs/features/import/markdown)），与「note 是唯一存储」**正面冲突**；TipTap 的**官方块拖拽把手**把 `@tiptap/extension-collaboration` + `@tiptap/y-tiptap` + `yjs` + `y-protocols` + `node-range` 写进必装清单（[drag-handle-react 文档](https://tiptap.dev/docs/editor/extensions/functionality/drag-handle-react)），等于把文档权威换成 CRDT，也冲突；Vditor 的 IR 模式**每次编辑都重新序列化**（官方 CHANGELOG 记着修过「WYSIWYG 和 IR 模式保存时会写入不换行空格」[#1938](https://github.com/Vanessa219/vditor/issues/1938)，2026-09 还在修「IR 输入 `- [ ]` 后回车把列表拆成两个 `ul`」[#1940](https://github.com/Vanessa219/vditor/issues/1940)），与「未碰块逐字保留」冲突，且它根本没有块重排能力（用户只能在 issue 里求思路 [#1236](https://github.com/Vanessa219/vditor/issues/1236)）；Slate 无官方 Markdown 序列化（69.7 KB gzip 最小，但映射层、块模型、把手全要自研）；**只有 Lexical 在官方层面带了「为往返保真而保存源文标记」的机制**（`@lexical/mdast` 的 source-based syntax preservation；并行会话还从 `@lexical/markdown` 源码里读到 `codeFenceState`/`listMarkerState`/`hardLineBreakState`/`codeMetaState` 这四个专为往返保真存在的状态，见附录 A §3.3——本文用 dist 复核时因 minify 无法命中符号名，**未独立证实**）——文档写明从 Markdown 字符串导入才有 *Source-based syntax preservation*（从 mdast 树导入时才不适用）、导出时 *Syntax preserved from import rides along as data fields on the nodes*、raw HTML *emitted verbatim*（[API 文档](https://lexical.dev/docs/api/modules/lexical_mdast)）；同时它的官方块把手 `DraggableBlockPlugin_EXPERIMENTAL` 只承诺 *reorder **top-level blocks***（[API 文档](https://lexical.dev/docs/api/modules/lexical_react_LexicalDraggableBlockPlugin)），而 ADR-0001 §6 恰好把拖拽**限定在顶层块序列**——劣势被决策消掉了。代价是：`@lexical/mdast` 与把手都标 **Experimental**，其依赖清单里没有 footnote 扩展（`mdast-util-gfm-footnote` 缺席，npm 元数据），而 ADR-0001 §5 要求「链接定义与脚注定义」是正式块类型；体积实测 **164.7 KB（走 `@lexical/markdown`）～202.8 KB（走 `@lexical/mdast`，上界）gzip**，在主包 484 KB / 1500 KB 警告线的约束下属中上。**综合六条硬约束，本票建议：Lexical（含 `@lexical/mdast`）第一、TipTap（自配把手、不用官方 DragHandle）第二、BlockNote 第三（且仅在 ADR-0001 被推翻时才该重新上桌）；自研 contenteditable 是唯一能 100% 守住「逐字保留」的路线但把 IME 全部风险揽给自己；在 Vditor 上加块层不推荐。**

## 2 六条硬约束逐条判定

**「六条」的出处说明**：票正文 `## 约束` 只列了 4 条 bullet（① 运行期零网络 ② React 19 + Vite 7 + TS strict ③ Markdown 为唯一存储 ④ 产物分发与体积）。本文另把两条也按硬约束判定，出处是票与地图/ADR 自己的措辞：**⑤ 中文 IME**——票第 3 核对点原话「这是本仓库的硬底线，见「不得回归清单」票」；**⑥ 顶层块拖拽把手 + 许可可随 Apache-2.0 分发**——地图 Destination 原话「块输入体验 + 拖拽把手调整块位置」，许可是票第 7 核对点。若 ⑤⑥ 不该算硬约束，判定结论需相应放宽（本文按算处理）。

### ① 运行期零网络（首要否决项）

**判定：六个候选都能通过，但通过的代价差别很大；只有 Vditor 属于「默认违规、已被本仓库改掉」。**

- **ProseMirror / TipTap / Lexical / Slate**：npm 发布物的 JS 里 grep `fetch(` / `XMLHttpRequest` 命中 **0**（本次实测 `prosemirror-view@1.42.6`、`@tiptap/core@3.32.0`、`@tiptap/react@3.32.0`、`@tiptap/markdown@3.32.0`、`@tiptap/extension-drag-handle@3.32.0`、`lexical@0.52.0`、`@lexical/react@0.52.0`、`@lexical/markdown@0.52.0`、`slate-react@0.147.3`），也没有 CDN 兜底、没有远程图标、没有语言包外拉。它们发布物里的 URL 字符串都是**注释/文档链接**（如 `@tiptap/core` 里的 `https://tiptap.dev/docs/...`、`lexical` 里的 `https://lexical.dev/docs/error`、`slate-react` 里的 `https://bugs.chromium.org/...`），实测不构成运行期请求。
- **样式资产**：ProseMirror 唯一必需 CSS 是 `prosemirror-view/style/prosemirror.css`（**0.5 KB gzip**，实测发布物）；TipTap / Lexical / Slate 发布物**不含 CSS**（实测 tarball 清单）→ 工具栏、把手、落点线样式全由本仓库 `src/index.css` 的 `[data-theme]` 变量供（地图「Not yet specified」里担心的皮肤问题，在 headless 路线上反而不存在）。
- **BlockNote**：`@blocknote/core` 发布物有 **4 处 `fetch(`**、**18 条 `@font-face`**、随包 **18 个 Inter 字体文件（347 KB raw）**；CSS 为 `core 5.5 + react 6.9 = 12.4 KB gzip`。这 4 处 fetch 具体打什么 URL **未证实**（本次只做模式计数，没逐处读上下文；`@blocknote/react` 导出名里有 `useResolveUrl`，最可能落在文件/图片块的 URL 解析钩子上）。→ 选它必须先审这 4 处 fetch 并证明可关；字体则要么 vendored（与 [sync 脚本第 16 行](../../scripts/sync-vditor-assets.mjs) 「不复制任何第三方字体文件」的现有口径冲突），要么覆盖掉它的 `@font-face`。
- **Vditor**：官方 README 的 options 表把 `cdn` 默认值写成 `https://unpkg.com/vditor@VDITOR_VERSION`，`hint.emojiPath` 默认也指 unpkg（[README](https://raw.githubusercontent.com/Vanessa219/vditor/master/README.md)）。本仓库已用 `cdn: assetRoot` 覆盖并 predev/prebuild 复制资产，所以**现状合规**，但这条合规是靠 356 文件 / 19.62 MB vendored 目录 + 一段 KaTeX MathML 适配补丁换来的（[sync-vditor-assets.mjs](../../scripts/sync-vditor-assets.mjs)、[MarkdownEditor.tsx:45,177](../../src/components/todo/MarkdownEditor.tsx)）。
- **自研**：零依赖，天然满足。

### ② React 19 + Vite 7 + TypeScript strict

- TS strict：`typescript: >=5.2` 出现在 `lexical@0.52.0` 与 `@lexical/react` 的 peerDependencies（npm 元数据），本仓库锁 `~5.8.3` 满足。`@tiptap/html` 另要求 peer `happy-dom ^20.8.9`，但**实测 `@tiptap/markdown` 的 dist 里 `happy-dom`/`@tiptap/html` 出现 0 次**（它只静态 import `marked` 与 `@tiptap/core`）→ 纯 Markdown 路线不会把 happy-dom 拖进浏览器包。
- Vite 7：**未证实**——本次未跑本仓库构建。候选均为标准 ESM；`@lexical/react` 用 `process.env.NODE_ENV` 三元在 dev/prod 产物间切换（实测 `dist/LexicalDraggableBlockPlugin.js` 只是一个 482 字节 wrapper），Vite 会 define 掉。
- 与本仓库全局接管的相处：本仓库在渲染前接管右键菜单与 autocomplete/spellcheck，并在富文本内抑制快捷键（`src/lib/shortcutKeys.ts`、`src/lib/shortcuts.ts`）。**所有候选都不阻止宿主接管**，但 TipTap/Lexical/Slate 的 contenteditable 都在组件内部，`data-autocomplete` 那套 MutationObserver 覆盖方式需按 06 票重测。

### ③ Markdown 为唯一存储（ADR-0001 已定稿）

**判定：BlockNote 与「TipTap 官方拖拽把手」与本约束正面冲突；「未碰块逐字保留」只有 Lexical 的 `@lexical/mdast` 给了官方机制，其余路线都要么必重写、要么自研。**

- **BlockNote**：官方两页均写 *"The functions to export to Markdown are considered \"lossy\"; some information might be dropped"*、*"not all structures can be entirely represented in Markdown"*，非 lossy 方案给的是 `JSON.stringify(editor.document)`（[export](https://www.blocknotejs.org/docs/features/export/markdown)／[import](https://www.blocknotejs.org/docs/features/import/markdown)）；import 侧限定为 *"a minimal Markdown parser… CommonMark + GFM basics: headings, paragraphs, lists, task lists, tables, code, blockquotes, links, images, emphasis, strikethrough, hard breaks"*，并直说 *"There are many Markdown specifications (CommonMark, GFM, MDX, Pandoc, and various dialect-specific extensions) and supporting all of them inside a rich text editor is not a goal of BlockNote"*（同页）。→ ADR-0001 §5 的**链接定义与脚注定义**、§4 的**Setext/引用式链接/两尾随空格**与「Mermaid/MDX/任意 HTML 原样进出」都不在其承诺范围；已知崩点 [#3189](https://github.com/TypeCellOS/BlockNote/issues/3189)（列表项以 `<details>` 开头时解析抛异常，open）。
- **TipTap 官方把手**：文档的安装命令逐项列出 `@tiptap/extension-drag-handle-react @tiptap/extension-drag-handle @tiptap/extension-node-range @tiptap/extension-collaboration @tiptap/y-tiptap yjs y-protocols`（[文档](https://tiptap.dev/docs/editor/extensions/functionality/drag-handle-react)）→ 权威文档模型变 Y.Doc，与 ADR-0001 §1（块是视图、不落库）与 §3（块 id 易失）冲突，也与本仓库「`db_save_state` 是唯一业务写入口 + 全量快照」的写链冲突。**若弃用官方把手、自己用已在用的 `@dnd-kit` 在外层做顶层重排**，TipTap 仍可停在 A 方案上。
- **Lexical**：`@lexical/mdast`（0.52.0，MIT，npm 元数据）是官方 mdast 管道：API 文档写明 `$convertFromMarkdownString` 之外还有 `$convertFromMdast`（从已解析 mdast 树导入时 *"Source-based syntax preservation does not apply (there is no source text to recover literal markers from)"*，反证**从 Markdown 字符串导入时会从源文恢复字面标记**）、`$convertToMdast`（*"Syntax preserved from import rides along as data fields on the nodes, mdast's sanctioned extension point"*）、raw HTML 片段 *"a string is raw HTML, **emitted verbatim**"*（[API 文档](https://lexical.dev/docs/api/modules/lexical_mdast)）。mdast 与本仓库只读侧的 remark/rehype 同族（[package.json](../../package.json) 已装 `remark-gfm`/`remark-math`/`rehype-*`），07 票的「块集合 ⊆ 只读语法子集」可共用一棵 AST 对齐。**风险**：整个包标 Experimental；其运行时依赖只有 `mdast-util-from-markdown`、`mdast-util-to-markdown`、`mdast-util-gfm-table/-strikethrough/-task-list-item/-autolink-literal` 与对应 `micromark-extension-gfm-*`，**没有 `mdast-util-gfm-footnote` / `micromark-extension-gfm-footnote`**（npm 元数据）→ 脚注这条 ADR-0001 正式块类型需自接扩展或实测降级。
- **ProseMirror 裸底座**：官方 Markdown 能力 = `prosemirror-markdown`（`MarkdownParser` 依赖 `markdown-it`；`MarkdownSerializer` 是按 schema 手写 token 输出，npm 元数据）。无「源文保留」概念 → **全文必规范化**，要做 ADR-0001 §4 得自己给每个节点挂源文区间（与自研同量级）。
- **Slate**：官方无 Markdown 序列化（三三包依赖表里没有任何 markdown 库，npm 元数据；docs.slatejs.org 未见 Markdown 章节——**未证实**，未逐页翻完）→ 等价于自研映射层。
- **Vditor**：保真天花板最高（Lute 覆盖 CommonMark+GFM 与脚注/公式等），但 IR 模式编辑即重排：官方 CHANGELOG v4.0.0 记录修复「WYSIWYG 和 IR 模式保存时会写入不换行空格」[#1938](https://github.com/Vanessa219/vditor/issues/1938)、v3.11.3/2026-09 仍在改 IR 列表行为 [#1940](https://github.com/Vanessa219/vditor/issues/1940)（[CHANGELOG](https://raw.githubusercontent.com/Vanessa219/vditor/master/CHANGELOG.md)）。本仓库 `docs/Markdown描述测试计划.md` 第 13 行也已写明「实际编辑后会重新序列化 Markdown…不保证源码逐字一致」——**ADR-0001 §4 是新的、更严的底线，Vditor 现状并不满足**。
- **自研**：唯一可 100% 实现「未碰块逐字节不动」的路线（源文↔块偏移自己掌握，透明块就是原样进出），代价见 ⑤。

### ④ 体积预算（主包现约 1.5 MB / gzip 484 KB，构建已有 1500 KB 警告）

**判定：增量从小到大 = 自研/Vditor(0) < Slate 69.7 < 裸 PM 109.8 < TipTap 精配 134.1 < TipTap+MD 147.5 < Lexical 164.7 < Lexical+mdast 202.8 < TipTap 官方把手 194.9（含 yjs 栈）<< BlockNote 352.8。**

- TipTap 最大单项是 `linkifyjs` **21.0 KB gzip**（随 `@tiptap/extension-link`→StarterKit 进来）：不用 Link 可从 147.5 降到 134.1。
- Lexical 的 `@lexical/mdast` 相对 `@lexical/markdown` 增加约 **38 KB gzip**（micromark + mdast-util 全家），且实测用 `import * as MD`（上界）。
- BlockNote 352.8 KB 的构成（按发布物字节/实测 gzip）：`@emoji-mart/data` **80.8**、`emoji-mart` **38.6**、`@floating-ui/react` **37.8**、`@tiptap/core` **68.8**、`prosemirror-view` **59.3**、`@shikijs/vscode-textmate` **18.9**、`@blocknote/core/dist/locales.js` 单文件 **268 KB raw**（多语言，可能按需加载）；另 `@blocknote/mantine` 的 peer 要 `@mantine/core ^8.3.11 || ^9.0.2`（npm 元数据，本测量设 external）→ 用默认 UI 还要再加 Mantine。→ 主包 gzip 会从 484 KB 涨到 **约 850 KB**，构建警告线直接被推翻。
- 本票不用「轻量」这类形容词；未实测的候选一律标未证实。

## 4 候选逐个补充证据（表内没放下的部分）

### A. ProseMirror（裸底座）与 TipTap

- **仓库迁移**：npm `repository.url` 已指向自托管 forge（`git+https://code.haverbeke.berlin/prosemirror/prosemirror-view.git`，`prosemirror-view@1.42.6` 与 `prosemirror-markdown@1.13.8` 元数据实测），GitHub 侧 `ProseMirror/prosemirror-view` API 返回 `archived: true`、`open_issues_count: 0`、最后推送 2026-04-01；发布仍在继续（311 个版本、最近 2026-09-25）。→ 维护风险不是停更，而是**单点自托管 forge**：排障检索要从 GitHub issue 换成 `code.haverbeke.berlin` 与 `discuss.prosemirror.net`，本仓库后续踩坑时不易被搜到。
- **裸 PM 的真实工作量**：官方只给 model/state/view/commands/keymap/history/schema-basic/schema-list/gapcursor（本文实测这套 + `prosemirror-markdown` = 109.8 KB gzip），**没有**块把手、斜杠菜单、表格 UI、浮动工具栏。TipTap 的 `@tiptap/core` 单项就 68.8 KB gzip，正是这些能力。→ 「裸 PM 更省」只在体积上成立，不在人力上成立。
- **`@tiptap/markdown` 的脚注**：实测其 dist 里 `footnote`/`Footnote` 命中 **0 次**（`table` 2 次、`hardBreak` 1 次）→ 脚注需自己写 marked tokenizer 扩展，与 ADR-0001 §5「链接定义与脚注定义」冲突。
- **TipTap 的 Markdown 现状**：文档把它归在 **ProseMirror Markdown（beta）** 分组，含 Introduction / Getting Started / Basic & Advanced Usage / **Custom Tokenizer / Custom Parsing / Custom Serializing** 与「把 Markdown 集成进你自己的扩展」指南（[文档导航](https://tiptap.dev/docs/editor/markdown/getting-started/installation)）；解析器是 **marked**（可注入自定义 marked 实例与 `markedOptions`，示例里 `gfm: true`、`breaks: true`；[API 页](https://tiptap.dev/docs/editor/markdown/api/extension)），序列化侧有 `indentation: { style, size }` 之类开关；官方节点表里有 Table / Table cell / Table row / Task list / Task item / Details / Details content / Details summary / Subscript / Superscript / Ruby / Mathematics / Hard break / Horizontal rule（同页导航实测）→ 与 ADR-0001 §5 的 12 类块对得上大半，**但没有任何一处官方声明「未碰块逐字保留」**（未证实：查过 markdown 三页，无支持矩阵也无已知限制清单）。
- **第三方 `tiptap-markdown`**（`aguingand/tiptap-markdown@0.9.0`，MIT，最近 2025-09-08）依赖 `markdown-it` + `markdown-it-task-lists` + `prosemirror-markdown`（npm 元数据）→ 与官方包并存，但发版节奏明显慢于官方；仓库内 README 的逐项保真说明**本次未取到**（raw 路径 404，分支名待核）。

### B. Lexical

- 官方自述（[intro](https://lexical.dev/docs/intro)）：*"It gives you a small, dependency-free core and a set of optional packages… so an application only includes the features it uses."* ——**全文没有任何 KB 数字**（实测该页不含 bundle/size 字样）。→ 体积必须自测，本文 §0 即为补齐这点；对外引用时不要写「Lexical 官方说很轻」。
- **两个 Markdown 包并存，选型必须先选一个**：`@lexical/markdown`（老的 transformer 机制，导出 `ELEMENT_TRANSFORMERS` / `MULTILINE_ELEMENT_TRANSFORMERS` / `TEXT_FORMAT_TRANSFORMERS` / `TEXT_MATCH_TRANSFORMERS` / `TRANSFORMERS`，实测 dist）与 `@lexical/mdast`（新管道，Experimental）。前者是「输入时快捷替换 + 正则式简写转换」（覆盖面窄：附录 A §3.3 从源码读到其导出清单**无 TABLE 转换器、无脚注、`HEADING_REGEX` 不认 Setext**，但同时读到 `codeFenceState`/`listMarkerState`/`hardLineBreakState`/`codeMetaState` 四个专为「活过往返」而存在的状态，**本文未独立复核**）；后者是 micromark + `mdast-util-to-markdown`（覆盖面由 GFM 扩展决定，且带源文标记保留）。**ADR-0001 §4 只能靠后者或自研满足**（前者没有源文保留概念）。
- `@lexical/mdast` 的运行时依赖（npm 元数据全文）：`lexical`、`@lexical/{html,link,list,table,utils,internal,code-core,extension,rich-text,selection}`、`@types/mdast`、`mdast-util-gfm-table`、`mdast-util-to-string`、`micromark-util-types`、`mdast-util-to-markdown`、`mdast-util-from-markdown`、`mdast-util-gfm-strikethrough`、`mdast-util-gfm-task-list-item`、`micromark-extension-gfm-table`、`mdast-util-gfm-autolink-literal`、`micromark-extension-gfm-strikethrough`、`micromark-extension-gfm-task-list-item`、`micromark-extension-gfm-autolink-literal`。**无 footnote、无 math**。→ 脚注要自接 `micromark-extension-gfm-footnote` + `mdast-util-gfm-footnote`（remark 生态常规做法，与本仓库只读侧 `remark-gfm` 同源）；行内公式本仓库现状由 `remark-math`/`rehype-katex` 承担，编辑期要么自接扩展、要么落 ADR-0001 §5 的「块级公式」+「透明块」。
- 把手：`DraggableBlockPlugin_EXPERIMENTAL` 文档原文 *"Experimental. Renders a draggable handle and drop-target line that let users reorder top-level blocks by dragging. You supply the handle and target-line elements via menuComponent / menuRef and targetLineComponent / targetLineRef, an anchorElem to portal them into (defaults to document.body), and an isOnMenu predicate"*（[API 页](https://lexical.dev/docs/api/modules/lexical_react_LexicalDraggableBlockPlugin)）→ 样式与图标由我们给（可复用 `lucide-react`），落点线自带；`@lexical/react` 的公开入口清单里**没有** `LexicalDragDropPlugin`（实测 exports 字段）。
- `@lexical/react` 发布物含 402 个文件、按插件分模块（实测 tarball 清单），配合 §0 的 external 设定实测整套 **164.7 KB gzip**；`lexical` 核心 min 后仅 199 KB raw（`Lexical.prod.js`），dev 版 1037 KB——**dev/prod 双产物是 Lexical 的发布形态**，生产构建不会把 dev 版打进包（实测 metafile 同时列出两者，说明 define 未必 DCE 干净 → 需在真实 `vite build` 后用 bundle 分析确认，见 §5）。

### C. BlockNote

- **fetch 计数口径**：本文对 `@blocknote/core/dist/*.js`（14 个文件）计数为 **4 处 `fetch(`、2 处动态 `import(`**；附录 A 数到 8 处（含未 minify 的 `src/`）。两处都说明「必须逐个证明可关」，且其中一处是 `resolveFileUrl` 取 blob 的路径。另实测 `@blocknote/core` 的 `peerDependenciesMeta` 把 `yjs`/`y-prosemirror`/`@y/*` 全部标 `optional: true` → **协作确实是可选的，这一点比 TipTap 的把手干净**。
- 表情与高亮是体积大头：`@emoji-mart/data` 80.8 + `emoji-mart` 38.6 = **119.4 KB gzip 只为表情选择器**；`@shikijs/vscode-textmate` 18.9 KB 为代码高亮。本仓库要的是「备注正文 + 把手」，这两项都能砍，但砍法要动它的默认 schema/UI（MPL 文件级 copyleft 让改动仍可分发，见 §2⑥）。
- 皮肤接入成本最高：自带 CSS `core 5.5 + react 6.9 = 12.4 KB gzip` + 18 个 Inter 字体；本仓库 5 套皮肤靠 `src/index.css` 的 `[data-theme]` 变量（[AGENTS.md 主题条](../../AGENTS.md)）。它确实提供 `@blocknote/shadcn`（实测有 `dist/style.css`，7.6 KB gzip）与本仓库 shadcn 基元同源，但仍带那 350 KB。
- `@blocknote/mantine` 发布物里**没有** `dist/style.css`（实测该路径不存在），但 `@blocknote/core`、`@blocknote/react`、`@blocknote/shadcn` 有 → 默认样式路径要按实际包核。
- 长文档性能有一条 open issue 与 09 票直接相关：[#2595 Typing/echo lag with many blocks (~50k chars total)](https://github.com/TypeCellOS/BlockNote/issues/2595)（2026-10 仍在更新）。其余候选未查到同量级主源证据（**未证实**：在 tiptap/lexical/slate 仓库搜过 lag/performance，本次未逐条读）。

### D. Slate

- 69.7 KB 里有**整包 `lodash`**：`slate-react@0.147.3` 与 `slate-dom@0.147.3` 都声明 `lodash: ^4.17.21`（npm 元数据），未 minify 的 `lodash.js` 实测 98.1 KB gzip。**能否被 tree-shake 未证实**（CJS 全量导入通常摇不动；本仓库若选 Slate 需要用真实 `vite build` 产物核实）。
- 能力缺口是它的本质：无官方 Markdown 序列化、无块模型、无把手、无斜杠菜单（三包发布物里没有任何 markdown 相关导出，实测）→ 选 Slate ≈ 把它当「带 IME 处理器的模型层」，其余全自研，实际工作量接近自研路线。
- **拖拽钩子缺失已由本文核实**：`slate-react@0.147.3` 的 dist 导出名里 `useDragSource`/`useDropTarget` 命中 **0**，而内部 `isDraggingInternally` 出现 8 次 → 内部有拖拽标记但不作为对外 API，块把手必须完全自接。
- 正面价值：`editable.tsx` 的 composition 分支与注释里的浏览器 issue 引用（实测发布物含 `https://bugs.chromium.org/p/chromium/issues/detail` 11 处、`https://issues.chromium.org/issues/389368412` 3 处、`https://developer.microsoft.com/en-us/microsoft-edge/platform/issues/10291116/` 1 处）是目前候选里**最完整的浏览器差异清单**，06 票的 IME 验收矩阵应按它逐项对照。

### E. 自研 contenteditable

- 权威行为定义：[W3C UI Events](https://w3c.github.io/uievents/#events-compositionevents) 的事件表把 `compositionstart` 标为 *"Sync / Update DOM / Show a text composition system candidate window"*，`compositionupdate`、`compositionend` 依次为 update/none，并要求 composition 期间的 `keydown`/`keyup` **MUST** 带 `isComposing=true`；另有 §3.6.3 Handwriting Recognition Systems、§3.6.4 Canceling Composition Events、§3.6.6 Input Events During Composition 三节必须逐条实现与验证。
- **MDN 的 contenteditable 页面本次未能抓取**（两次连接超时）→ 本文不引 MDN 原文；**未证实**：`developer.mozilla.org/en-US/docs/Web/HTML/Reference/Global_attributes/contenteditable`。ProseMirror 作者对浏览器 DOM 难度的表述只在 guide 里间接可见（*"The browser is quite good at cursor and selection placement… which is a really difficult problem when you factor in bidirectional text"*，[guide](https://prosemirror.net/docs/guide/)）；**没有**找到「不要自己写 contenteditable」这类直白告诫的主源原文，本文不代其立论。
- 本仓库已付的学费：ADR-0001 §4 的「透明块原样进出」+ §7 的「dirty = 序列化结果 !== 原文」其实就是自研路线需要的两块地基，`lastSent`/`lastRendered` 双 ref 已实现「未编辑不改写」（[MarkdownEditor.tsx:211-212](../../src/components/todo/MarkdownEditor.tsx)）——**但「编辑过的块之外全部逐字保留」这一步现状仍没做**（Vditor IR 会整体重排），所以无论选谁，这一层都得新写。

### F. 在 Vditor 4.0.0 上加块层

- 保真能力来自 **Lute**（Go 编译成 JS）：`dist/js/lute/lute.min.js` 实测 3655.6 KB raw / **587.6 KB gzip**；README 的 emoji 与语法配置直接引用 `88250/lute`（[README](https://raw.githubusercontent.com/Vanessa219/vditor/master/README.md)）。→ 这是「保真换体积」的既有价格，换引擎时它可以被省掉（新引擎不再需要 Lute）。
- **块层可行性**：官方 options 有 `customRenders`（README 出现 `customRenders: {la…`，即可自定义渲染），**但没有块重排 API**；相关 issue 全落在图片/大纲/尺寸拖拽，文字块重排只有 [#1236 我想开发一个拖拽文字内容的需求，请求一个思路](https://github.com/Vanessa219/vditor/issues/1236)（closed）与 [#986 编辑器内图片拖拽](https://github.com/Vanessa219/vditor/issues/986)（open）。→ 把手要完全自己做，且要挂在 IR 模式非公开的 DOM 结构上，脆弱度与「shadcn 基元勿手改」同级。
- **版本与安全**：npm 最新 `4.0.1 / 2026-10-18` 修复 **媒体渲染 XSS**（GHSA-x2mx-f527-mxr9）、升级 Mermaid 11.17.2、新增 `options.preview.markdown.inlineMath`（[CHANGELOG](https://raw.githubusercontent.com/Vanessa219/vditor/master/CHANGELOG.md)）；本仓库 [package.json](../../package.json) 锁 `vditor 4.0.0`。→ **与本票结论无关但应单独评估升版**。

**B. 需要人拍板的三点**（本文只摆事实）：

1. **`@lexical/mdast` 的 Experimental 能不能当地基**。这是本票的核心分歧：ADR-0001 §4「未碰块逐字保留」在 Lexical 上只有这个包能撑，而包名后缀写着 Experimental（[API 页](https://lexical.dev/docs/api/modules/lexical_mdast) 的类型条目多处标 *Experimental*）。若不接受 Experimental，就得选「TipTap/裸 PM + 自研源文区间映射」或干脆自研——**用实现成本换确定性**。
2. **脚注与数学的补齐方式**：`@lexical/mdast` 依赖清单里没有 footnote/math（§4.B），要么自接 `micromark-extension-gfm-footnote` 等扩展（与只读侧 `remark-gfm`/`remark-math` 同源、成本可控），要么把脚注降级成透明块（**与 ADR-0001 §5 冲突，需改 ADR**）。这条要 07 票一起定。
3. **体积上限给多少**：主包 gzip 484 KB、构建 1500 KB 警告线在等。上限 200 KB → Lexical 可行；上限 150 KB → 只剩 Slate/TipTap 精配；只接受 0 新增 → 只剩自研/Vditor 块层（两者都把最大成本搬到人月）。顺带决定是否允许「把 Vditor + Lute 的 587.6 KB 懒加载从产品里彻底移出」。

**C. 与验收口径有关的实测项**（06 票负责手段，本文只列风险）：① 引擎内撤销栈 vs 浏览器原生撤销在 WebView2/WebKit 上的跨块语义（ADR-0001 §7 用字符串比较判 dirty，可绕开一半问题）；② React StrictMode 重挂载不产生重复编辑器实例（Vditor 侧历史坑 [#1658](https://github.com/Vanessa219/vditor/issues/1658)）；③ dev/prod 双产物在真实 `vite build` 后是否摇掉（§4.B，本测量里两者同时出现在 metafile）；④ 四条 flush 路径（blur / pointerdown 离开 / pagehide / `todo-save-draft`）能否在引擎 debounce 之外**同步**取到序列化结果；⑤ 图片链路（选择/粘贴/拖入 → 压缩 → 附件 → `attachment://` 回写）与新引擎选区恢复的配合。

## 6 推荐排序（给决策票的输入，不是决定）

1. **Lexical 0.52 + `@lexical/mdast`（第一推荐）**。理由：ADR-0001 最硬的两条——§4 未碰块逐字保留、§6 拖拽只在顶层——**只有 Lexical 在官方层面同时给了机制**（mdast 源文标记保留 + `DraggableBlockPlugin_EXPERIMENTAL` 的顶层块重排）；MIT + Meta 维护 + 发版最勤；IME 有专门的浏览器回归基建（PR #8793/#9362/#8942）；无 CDN、无字体、无自带 CSS，零网络与 5 套皮肤都好办；mdast 与只读侧 remark/rehype 同族，07 票的语法子集对齐可共用一棵树。**最大风险**：`@lexical/mdast` 与把手都标 Experimental，且其依赖不含脚注/数学扩展（要自接）；体积 164.7–202.8 KB gzip 属中上；一旦实测发现「源文保留」不覆盖全部 12 类块，退路就是自研一层源文区间映射（成本回到自研路线）。
2. **TipTap 3 + `@tiptap/markdown`，且不使用官方 DragHandle（第二推荐）**。理由：体积比 Lexical 小（134.1–147.5 KB）、扩展生态与节点表最贴本仓库语法面（Table/Task list/Details/Sub/Sup/Ruby/Mathematics）、Markdown 侧开放 Custom Tokenizer/Serializer 有自救面、MIT + 商业公司持续发版、React 19 明确在 peer 里。**最大风险**：**官方拼音 issue [#4084](https://github.com/ueberdosis/tiptap/issues/4084) 至今 open**，直接压在硬底线 ⑤ 上；`@tiptap/markdown` 仍是 beta；块把手必须自接 `@dnd-kit`（顶层序列重排要自己写 decoration 与落点计算）；「未碰块逐字保留」**没有任何官方机制**，从第一天起就要自研源文映射。
3. **BlockNote 0.56（第三，且带前提）**。理由：唯一把 Notion 交互（Side Menu + Drag Handle + 可替换菜单 + 斜杠菜单）现成交付的候选，React 19 与 IME 都在正常维护。**最大风险**：**与已定稿的 ADR-0001 §1/§4 正面冲突**（官方写明 Markdown 双均 lossy、非 lossy = JSON 文档），叠加 352.8 KB gzip + 12.4 KB CSS + 347 KB 字体、MPL-2.0 的文件级 copyleft 义务、以及 4 处未审计的 `fetch`。**只有当 ADR-0001 被推翻、改判结构化块存储时它才该重新上桌**；否则它在 06 票「不得回归」与 07 票「语法子集一致」两条上都会持续付账。
4. **不推荐**：① **在 Vditor 上加块层**——保真与零网络最好，但引擎无块重排能力、DOM 非公开 API、并且**违反 ADR-0001 §4**（IR 每次编辑整体重排，官方自己修过 [#1938](https://github.com/Vanessa219/vditor/issues/1938)/[#1940](https://github.com/Vanessa219/vditor/issues/1940)）；顺带单列一条与本票无关的发现：**本仓库锁的 4.0.0 缺 4.0.1 的 XSS 修复，无论换不换引擎都应评估升版**。② **纯 Slate**——IME 底座扎实、体积最小，但 Markdown 映射、块模型、把手三块全自研，实际等价「自研 + 一个好底座」。③ **自研 contenteditable**——0 KB 新增、唯一能满配保真，代价是把 [UI Events §3.6](https://w3c.github.io/uievents/#events-compositionevents) 之外的全部浏览器偏差与验收矩阵揽到自己身上，而 IME 恰是本票认定的硬底线；若前两者的 Experimental/IME 风险在 05 票原型里都不可接受，它才是第三条路。

### 3.6 自研 contenteditable

- 规范面：`contenteditable` 是**枚举属性**（`true`/``/`false`/`plaintext-only`），MDN 明确「If content is pasted into an element with `contenteditable="true"`, **all formatting is retained**；… `plaintext-only` → all formatting is removed」，并说明嵌套 editable 默认不进 Tab 序列（要 `tabindex="0"`）——https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Global_attributes/contenteditable。**未证实**：MDN 该页本次没有抓到「跨浏览器行为不一致」的成文警示。
- 现实难度：ProseMirror 官方指南逐字承认「**Even typing is usually left to the browser, because interfering with that tends to break spell-checking, autocapitalizing on some mobile interfaces, and other native features. When the browser updates the DOM, the editor notices, re-parses the changed part of the document…**」（https://prosemirror.net/docs/guide/）——即「浏览器改 DOM、编辑器事后重解析」就是最成熟实现的方案；而 PM / Lexical / Slate 三家都各自写了组合状态机（见 §3.1/3.3/3.5 源码），等于三份独立证据表明这一段不能省。
- 与本票主线的关系：**Markdown↔块这一层无论选谁都要自研**（ADR-0001 §4「未碰块逐字保留」、§5「透明块原样进出」），所以自研路线相对「PM/Lexical + 自研 md 层」的差额只是**编辑表面**那部分，而那部分恰恰是 IME 底线（P0-10）与撤销语义（FIX-02）风险最集中的地方。结论：自研在「保真可控度」上最高，在「IME 风险」上最差。
- 体积：0 第三方；权威 md 层若用 remark/micromark 同源，实测 26.3～36.4 KB gz（§2 表末三行）。

### B.1 `@lexical/mdast` 的官方覆盖面（源码逐字 + 官方文档页）

- **官方文档页**：https://lexical.dev/docs/packages/lexical-mdast （页面顶部即 **`⚠️ Experimental: everything in this package is marked @experimental and may change between any two Lexical releases — including breaking renames, signature changes, or behavior changes — until the API stabilizes. @lexical/markdown remains the supported default for production apps that don't want to track an experimental API.`**）。
- **保真机制的官方原话**：`Like @lexical/markdown, the original syntax of a construct is preserved on the Lexical nodes (the bullet character of a list, a code block's fence, and a hard line break's style), so re-serializing produces minimally different Markdown — * a / + b bullets and ~~~ fences round-trip unchanged.`
- **对实施有直接影响的限制（官方原话）**：`… source text themselves (which is also what enables source-based syntax preservation, e.g. keeping * vs - bullets); the *FromMdast functions take an already-parsed tree, where no source text exists so syntax preservation is skipped.` → **必须从「Markdown 字符串」入口进入才享受源文保真；把外部（例如只读侧 remark）已经解析好的 mdast tree 直接喂进来，保真机制就整条失效。** 这条决定了 §5「只读渲染器与块编辑器是否共用 AST」只能选「共用 parser 包、不共用 tree 中间产物」。
- **扩展表（文档页 + 源码 `@lexical/mdast/src/MdastGfmExtension.ts`）**：CommonMark 面 = `MdastHeadingExtension`（**ATX & setext headings**）、`MdastBlockquoteExtension`、`MdastListExtension`（有序/无序）、`MdastCodeExtension`（**fenced & indented code**）、`MdastLinkExtension`（links、`<autolinks>`、**reference links**）、`MdastHorizontalRuleExtension`；GFM bundle = `MdastStrikethroughExtension` + `MdastTaskListExtension` + `MdastAutolinkLiteralExtension` + `MdastTableExtension`（源码注释：`mirroring the scope of micromark-extension-gfm`，并说明 `Each member is also usable individually… e.g. task lists without tables`）。
- **脚注 / 数学不在这套 bundle 里**：`@lexical/mdast@0.52.0` 的 `dependencies`（实测 npm 发布物 package.json）里有 `mdast-util-gfm-table / -strikethrough / -task-list-item / -autolink-literal` 及对应 4 个 `micromark-extension-gfm-*`，**没有** `micromark-extension-gfm-footnote`，也**没有**任何数学扩展；文档页 `footnote`/`math` 字样各 0 命中。唯一痕迹是 `src/index.ts` 的类型清单里出现 `FootnoteDefinition, FootnoteReference`、`src/MdastExport.ts` 有一句注释 `handler that appends end-of-document data (footnote definitions, …)`、`src/MdastHtmlExtension.ts` 出现 `'footnoteDefinition'` 字面量 → **说明留了自定义 handler 的通道，但开箱不解析脚注**（判读，需实测）。这与 ADR-0001 §5「链接定义与脚注定义固定文档尾部、不可拖拽重排」正好对得上：要做得自己写这两个 handler。
- **「不丢弃」有据、但「原样进出」无据**：`src/MdastExport.ts` 注释原文 `Fallbacks keep unknown nodes from disappearing entirely; text and line …` 与 `Fallback: unwrap unknown containers, render unknown literals as text, and …`，全文 `throw` 0 处、`not supported`/`unhandled` 0 处 → 不会抛错、不会凭空删节点；但「render unknown … as text」是否等价于 ADR §5 要的**透明块原样进出**，**未证实，必须实测**（Mermaid / MDX / 任意 HTML 三类）。
- **源码里能看到 ADR-0001 §4 那种做法的实现**：`ctx.source` + `node.position.start.offset` 切片回原文（`const raw = ctx.source.slice(start.offset, end.offset).replace(/\n$/, '')`），另有 `Preserve the literal marker the list used so export can reproduce it` / `Preserve the literal fence (e.g. \`\`\` vs ~~~ vs \`\`\`\`) for round-tripping` / `An mdast break is always a HARD break; preserve whether it was written…` 三处注释与 `verbatim` 出现 5 处。

### B.2 `@lexical/mdast` 路线的实测 gzip（补进正文 §0/§4 的对照）

口径同附录 A §2（esbuild bundle+minify、入口 `import * as 命名空间` 全导出＝上界；react/react-dom/katex/yjs 外部化）：

| 组合 | 实测 gzip |
| --- | --- |
| `@lexical/mdast` 本体（lexical 族外部化，只算它自己带进来的 micromark/mdast 一族） | **39.2 KB** |
| `lexical` + `@lexical/rich-text` + `@lexical/mdast`（不含 React 绑定） | **187.3 KB** |
| Lexical 全套（react 插件 + DraggableBlock + list/checklist/link/table/code/utils + **mdast**） | **206.3 KB** |
| 对照：正文/附录 A 里不含 mdast 的 Lexical 基线 | 142.1 KB（基线）／174.9 KB（全扩展） |

→ 结论性数字：**选 `@lexical/mdast` 相对旧 `@lexical/markdown` 路线要多付约 30～60 KB gzip**（上界口径；`@lexical/markdown` 若同时不用可抵扣一部分）。与「自研 md 层 + remark/micromark 同源」方案对照：`unified + remark-parse + remark-stringify` = 26.3 KB、再加 `remark-gfm`（**含脚注**）= 33.8 KB、再加 `remark-math` = +2.6 KB（约 36.4 KB）——即**两条路的解析器体积几乎相同，差别在「谁来实现逐字保真与块级序列化」**：走 `@lexical/mdast` 是拿官方实现（但标 `@experimental`、缺脚注/数学、且必须从 Markdown 字符串入口进），走 remark 是拿社区稳定 API 但要把 mdast→块→mdast 的映射与未碰块原文自己写完。

### B.3 两套 gzip 数字为什么对不上（口径说明，免得决策时被两个数搞混）

- 本票（附录 A/B）：入口写成 `import * as ns from '<pkg>'` 并导出全部符号＝**不做摇树的上界**，且按我选的功能组合取包（TipTap 侧我算了 starter-kit + extensions + markdown + 表格 + 任务列表 = **174.4 KB**；再加官方 DragHandle 连带 `@tiptap/extension-collaboration` + `@tiptap/y-tiptap` + `yjs` = **228.7 KB**，即把手本身 **+54.3 KB**）。
- 正文 §0/§4（另一会话）：TipTap 记 134.1～147.5 KB —— 明显是**按最小入口且能摇树**的口径。
- 两者都成立，**不能混用**；正式定体积时以本仓库一次真实 `npm run build` + 产物分析为准（本文所有数字都只是选型阶段的相对量级）。
- 唯一不受口径影响的对照：**BlockNote 是最大的（350～460 KB 量级）**、**Slate 最小（73～75 KB 但功能面最薄）**、**Vditor 现状 124.0 KB gz（minify 后下限 72.6 KB）+ 20.57 MB 运行期资产**。

### B.4 与 IME / React 19 有关、正文未列的一条源码级事实

- `@lexical/mdast` 与 React 无关，但它的存在改变一条判断：正文说「Lexical 的 markdown 面缺口最大（无表格/脚注/Setext）」——那是 **`@lexical/markdown`** 的事实（源码 `HEADING_REGEX=/^(#{1,6})\s/`、`TRANSFORMERS` 无 TABLE）。改用 `@lexical/mdast` 后 **Setext / 缩进代码 / reference links / 表格都有官方 handler**，缺口只剩**脚注与数学**（见 B.1）。两条主张并存是因为两会话取的是不同包；以本节为准。
